## Gate decision and status

Complete. CPU prompt lookup pays on the evaluated code and RAG-style workloads. It also clears the binding kill line on the open-continuation control, but that control has substantial repeated generated text. Summarization loses and must remain disabled. This is a workload-conditional result, not a recommendation to enable lookup for all requests.

The kill line requires at least 1.15x decode wall throughput versus unchanged v2 and a 95% prompt-bootstrap lower bound strictly above 1.0x. Code, RAG and the evaluated continuation control pass. Summarization fails. Since categories pass, the card-wide "not worth shipping" kill condition does not trigger.

Owned deliverables are `spec/` and this report. No kernel fork was necessary. No git write command or private `research/` file was used.

## Workloads and measurement method

- Fixed seed 25, 20 prompts in each of four categories, 80 total [measured, `spec/prompts.jsonl`]. Prompt lengths span 128 to 1901 tokens. Outputs are 64, 96, 128 or 256 tokens, fixed-length greedy decoding without an EOS early exit.
- Code asks for docstrings and a variable rename while rewriting excerpts from public CPython 3.12.14 `ast`, `functools`, `heapq`, `statistics` and `collections` source. Each prompt records its public source URL, source hash and token offset. These are file excerpts, not an application benchmark.
- RAG-style prompts ask for exact continuation of a quoted cue from a provided WikiText-2 test passage. Summarization asks for three sentences from a passage. Open continuation asks for original discussion rather than quoting its passage. No answer-quality claim is made for this 0.6B base model.
- Three same-process interleaved repeats per prompt, rotating/reversing variant order. Each engine prefills its own real prompt KV, restored before each run outside the timing window. Eight-token warmups precede measurement. GPU jobs use `scripts/gpu.sh`, each bounded to 285 seconds, with `--timing` for throughput.
- Decode wall time starts before lookup-index construction and ends after all output tokens are on the CPU. It includes CPU drafting/index maintenance, host/device token and position traffic, synchronization, target launches, target-sampler token return, verification, logical rollback and trace bookkeeping. It excludes weight loading, corpus tokenization, warmups, prefix-state restore and prompt prefill. This is end-to-end decode throughput, not GPU-event throughput or full request latency. Prefill-inclusive rates are separately reported below.
- Plain v2 uses its real existing `mega(count)` multi-step persistent launch and one final token-history return. It is not slowed into a Python per-token straw baseline. Plain mt3 M1 uses the same host wrapper as the speculative target without drafting.
- Category throughput is total output tokens divided by summed per-prompt mean wall time. Speedup is the ratio of those totals. CIs resample paired prompts 10,000 times with seed 25; repeats are averaged within each prompt, never treated as independent confidence samples. CIs do not capture model, corpus or device uncertainty.

Public sources are CPython at the per-prompt GitHub URLs and `Salesforce/wikitext`, configuration `wikitext-2-raw-v1`, test split. Prompt lookup follows the reuse idea in arXiv 2411.10666; no suffix automaton or small-model drafter is used. Mainardi et al., EACL 2026 is relevant to the distinction between draft acceptance and wall speedup, not an empirical source for this card.

The policy begins with a limit of k=4. Full draft acceptance grows the limit by one up to 5; rejection shrinks it by one down to 2. No suffix match means actual k=1. Available continuation length and remaining output budget also reduce actual k. Lookup checks suffixes from 24 tokens down to 1, choosing the latest previous occurrence at the longest available n-gram length, over prompt plus accepted generated tokens. Only accepted tokens enter the index. There is no learned model or category-specific tuning.

## Rollback and verification semantics

A pass consumes the last known token as its anchor plus up to k-1 drafts. Column i returns the target argmax after input i. The verifier accepts the longest matching draft prefix, then commits the first correction or final bonus token. It advances logical position by accepted drafts plus one. The newly known target token has no KV yet and is the next anchor.

Mt3 causal attention bounds historical reads by each query position and materializes new rows locally. The next call writes its explicit base position, so rejected rows remain physically allocated but are ignored. The next anchor overwrites the first rejected row before it can become visible; later rows are likewise overwritten before entering the logical prefix. There is no KV memcpy or clearing rollback. Shared KV buffers let all k specializations use the same accepted prefix. Rejection-at-zero, partial acceptance and full acceptance all appear in the retained trace and all-prompt identity check.

## Honest negatives and open threads

- Summarization is 0.919x v2 with CI entirely below one. Do not ship lookup there with this policy.
- The expected low-acceptance open control was not uniformly low. Mean repeated generated four-gram fraction is 41.78%, compared with 17.99% for code, 26.98% for RAG and 4.62% for summarization [derived, `analyze.py`, mean of `1 - unique output four-grams / output four-grams`]. Lookup uses generated history as requested, so repetitive continuation can accept many drafts even without useful prompt copying. This base-model/fixed-length workload is not evidence for general instruct-chat speedups.
- V2 and mt3 take different branches on 13.75% of prompts. The integrator-approved speed comparison is between two HF-gated targets, not a promise of byte-identical output to v2. Speculation itself remains exactly lossless to mt3.
- Lookup n-grams are capped at 24. Python indexing costs CPU time and memory proportional to history length times that cap. No SAM, long-session compaction, stochastic sampler or small-model draft engine was evaluated.
- CIs cover 20 selected prompts per category, not a corpus-wide guarantee. Unlocked device clocks limit cross-session absolute comparisons; variants are paired within each prompt.
- No implementation or evaluation work remains for LM-25. Open research questions are task-quality-aware continuation controls and whether this policy pays at 8k. Neither is needed to interpret the completed short-to-2k result.
