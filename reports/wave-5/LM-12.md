# LM-12: Qwen3-1.7B decode scale

## Gate decision

Corrected 1.7B FP32-accumulate engine: **gate v2.1 PASS** on 3 x 64 teacher-forced tokens vs CPU HF fp32 fake-quant, no hard argmax flips, bitwise identical repeated logits. FP16-HFMA2 inheritance failed and is not timed `[measured, bench/lm12/check_gate_v21.py → bench/lm12/gate_v21.json]`.

## Status

The Qwen3-1.7B-Base cached `config.json` confirms hidden 2048, intermediate 6144, 28 layers, 16 query/8 KV heads, head dimension 128, tied embeddings and vocabulary 151936 `[measured, ~/.cache/huggingface/hub/models--Qwen--Qwen3-1.7B-Base/snapshots/ea980cb0a6c2ae4b936e82123acc929f1cec04c1/config.json]`. This is an independent fork; the 0.6B v2 code and artifacts are unchanged.

The scaled kernel builds on sm_75 with 36 CTAs x 1024 threads, 64 registers, 22144 bytes SMEM per CTA and **0 spill stores/loads in the timed `mega2_kernel`** `[measured, nvcc -O3 -arch=sm_75 -Xptxas=-v kernels/megakernel_scale/mega_scale.cu]`. NC=2 for every hidden-width input projection, including o-projection; NC=6 for down-projection. `kernels/megakernel_scale/sched_scale.py` emitted context 128/2048/8192 schedules, each 5148 tasks and 143 flags; `validator/target/release/schedcheck` returned **ACCEPT on all three** `[measured, sched_scale.py; schedcheck]`.

Calibration and GPTQ packing now cover every layer and the tied head. Seven layer-range Hessian files record the same 128 seeded training windows. `bench/lm12/gptq_pack.py merge` wrote 113 packed matrices plus fp32 reference reconstructions `[measured, bench/lm12/run_calibration.sh]`. The new timed build uses FP32 code*activation accumulation. Its 64-register, 22144-byte-SMEM kernel has zero ptxas spills; the original FP16-HFMA2 path remains as an untimed diagnostic `[measured, nvcc -DFP32_DOT -Xptxas=-v kernels/megakernel_scale/mega_scale.cu]`.

Reproduce in order: `kernels/megakernel_scale/build.sh`, `bench/lm12/run_calibration.sh`, `scripts/gpu.sh .venv/bin/python bench/lm12/check_gate_v21.py`, `bench/lm12/prepare_gguf.sh`, `bench/lm12/run_ppl.sh`, then `bench/lm12/run_timing.sh`. The calibration script uses individual GPU jobs bounded by its per-job timeout; timing invokes `scripts/gpu.sh --timing` one context at a time. `bench/lm12/results.jsonl`, `gate_v21.json` and `ppl.json` contain the machine-readable evidence.

## Honest negatives

The 1.7B fp32 HF model exceeds the available GPU memory alongside calibration Hessians. `bench/lm12/calibrate.py` collects fp32 Hessians from fp16 model activations over the same seeded 128 x 2048 WikiText-2 training windows as LM-11, in layer ranges; this differs from LM-11's fp32 calibration activations. First range failed after 128 windows while saving because inference tensors disallow in-place post-context division; fixed before rerun `[measured, scripts/gpu.sh .venv/bin/python bench/lm12/calibrate.py 0 1]`. CPU fp32 reference remains required for the gate.

Layer 0:4 calibration succeeded with 16 fp32 input-Hessian matrices `[measured, scripts/gpu.sh .venv/bin/python bench/lm12/calibrate.py 0 4]`. The next 4-layer range hit CUDA OOM at 256 MiB allocation when another process occupied 1.72 GiB VRAM; the live model plus on-device Hessian sums would not fit `[measured, bench/lm12/run_calibration.sh → calibrate.py 4 8]`. `calibrate.py` now moves each fp32 covariance to CPU before accumulation so calibration still uses all 128 windows without storing multiple layer Hessians on GPU. The same recorded GPTQ algorithm packed layer 0 successfully in 7.46 s `[measured, scripts/gpu.sh .venv/bin/python bench/lm12/gptq_pack.py 0]`.

With CPU accumulation, range 4:8 completed all 128 windows; range 8:12 reached window 112 before the 300-second per-job deadline `[measured, bench/lm12/run_calibration.sh]`. Subsequent incomplete ranges now run four disjoint 32-window jobs and merge their fp32 Hessians on CPU. Layer 0 packed tensors reconstruct the recorded GPTQ dequantization bit for bit on all four matrices `[measured, bench/lm11/ppl_llama_protocol.py deq_int4 against bench/lm12/deq.0.pt]`.

The initial v2 FP16-HFMA2 arithmetic collapsed on this larger model: max finite |logit diff| 24.6176 across 3 x 64 forced steps and NaN logits late in each sequence. The FP32-accumulate diagnostic with the same packed weights, cached KV representation and model yielded max |logit diff| 0.05154 and no hard argmax flips `[measured, bench/lm12/check_gate_v21.py → gate_v21.json, initial run]`. This is a numerical stability failure of the inherited half dot product, not evidence that the 1.7B model is inherently unsuitable. The diagnostic arithmetic now drives the timed kernel; its speed must be measured honestly.

At ctx8192 the first attempt kept both engines' allocations resident. llama-bench failed to create its context alongside the packed weights, the megakernel's 8704-position fp16 KV caches and desktop VRAM use `[measured, bench/lm12/run_timing.sh → interleave.py]`. The ctx8192 retry frees/reloads the megakernel between timed v2/llama slices. Loading is outside both timing windows; the model/quality/cache/attention settings are unchanged, but this memory accommodation must be disclosed alongside its result.

4B stretch was investigated **after** the complete 1.7B gate, quality table and three context pairs. Its official config confirms hidden 2560, intermediate 9728, 36 layers, 32 Q/8 KV heads and head dimension 128 `[measured, Qwen3-4B-Base config.json, revision 906bfd4b4dc7f14ee4320094d8b41684abff8539]`. The BF16 checkpoint index lists **8,045,591,552 bytes = 7672.9 MiB**; the contemporaneous GPU had **4877 MiB free**, a **2795.9 MiB deficit before activations/Hessians** `[measured, Qwen3-4B-Base model.safetensors.index.json; scripts/gpu.sh nvidia-smi --query-gpu=memory.total,memory.free,memory.used; derived MiB conversion]`. A CPU fp32 copy is **15,345.7 MiB** `[derived, checkpoint index]` and could fit system RAM, but the 4B weights are not cached locally and no 4B gate was run. The existing two-CTAs-per-query-head attention mapping would require **64 CTAs**, exceeding the 36 resident CTAs required by this kernel's full-grid barrier. Also hidden 2560 and intermediate 9728 are not multiples of 1024, so the current NC=2/4/6 GEMV would miss partial lane chunks without masking `[derived, config.json; kernels/megakernel_scale/mega_scale.cu]`. A real 4B port needs streamed/offloaded calibration, one-query-head-per-CTA attention and masked NC=3/10 weight reads. None of those changes or their 4B correctness/quality/timing gates were completed. **No 4B speedup claim.**
