## Gate decision

**KILL the MMA replacement. Retain mt2 CUDA-core GEMM unchanged.** The best MMA path loses every shape at M1 and M2. At M4 it wins qkv, gate/up and the head by 2.41%, 7.16% and 9.15%, but loses the output and down projections [derived, `shapes.json`]. Its gains are too small for the wave's pass target.

The integrator explicitly stopped the mixed-dispatch gate, selected no GEMM change for merging, and requested this measured negative. Applying those three shape percentages to LM-18's corresponding M4 persistent durations gives an optimistic saving of approximately 0.086 ms, not the required approximately 1.1 ms [derived, LM-18 phase table and `shapes.json`; assumed transfer of standalone percentages to persistent code]. That estimate is not a full-pass measurement.

Choosing CUDA cores at M1 and FP32-accumulating MMA at M4 would also change the arithmetic used by speculative verification. Exact same-engine sequential logits cannot be inferred from the CPU-reference check. That mixed dispatch was not gated and is not offered as a valid engine. An all-MMA persistent M4 build spills and was excluded from timing.

## Status

Owned paths are `kernels/megakernel_mma/`, `bench/lm22/` and this report. The fork adds an opt-in `MMA` include only. Its default production include remains mt2's unchanged `gemm_preload.cuh` and `gemm_nv.cuh`. No baseline kernel, gate code, git state or private research was changed.

The fragment kernel works for M=1 through 8, with inactive B columns zero-filled. The inherited full-pass Python ABI still accepts M=1 through 5. No extension of full-pass attention or prologues to M=6 through 8 was attempted.

Implemented design:

- A is the unchanged row-major INT4-g128 weight matrix. Four lanes load four adjacent 32-weight `uint4` chunks for each row, covering one 128-weight scale group. Each lane owns rows `lane/4` and `lane/4+8`; shuffles select each packed word. The existing `0x6400` conversion and explicit half2 FMA dequantize directly into A registers. The group's FP16 scale and offset are reused for all its 128 weights.
- B contains token columns `lane/4`. Each lane supplies the adjacent K pair at `2*(lane%4)`. The matrix instruction is `mma.sync.aligned.m16n8k8.row.col.f32.f16.f16.f32`.
- Four FP32 accumulator registers hold two token columns for each of the two output rows. Output is converted to FP16 only for non-head shapes.
- Split-K factors 1, 4 and 8 use deterministic shared-memory reductions. Split 1 wins the larger-output shapes; split 8 best fills the small-output shapes. Neither changes weight files.
- A GEMM-local, register-backed in-place activation transpose plus token-column XOR bank swizzle fixes the direct B-load bank pattern. It adds two CTA barriers, but no second activation allocation. Width-specialized staging removes runtime integer divisions for the supported shapes.

### Fragment correctness

[measured, `fragment_check.py` -> `fragments.json`] The final split-1 swizzled kernel passes 32 CPU-exact cases: every M from 1 through 8, input widths 128/1024/2048/3072, and output row counts 17/35/33/16. The non-multiple-of-16 rows exercise masked output tails. Maximum absolute error is 0.0. Dyadic scales, offsets and activations make this a strict fragment/layout oracle rather than a tolerance test.

[measured, `fragment_check.py` -> `fragments-split.json`] An additional 36 saved cases cover split factors 1/4/8 at M1/M2/M4 on the same four shapes. Maximum absolute error is also 0.0.

[measured, `shape_probe.py` -> `shapes.json`] Before timing, 35 actual GPTQ rows per shape are checked against an FP32 CPU dot product of FP16-dequantized weights. The largest final MMA error is 0.0000023842. This check covers non-dyadic real scales and offsets at M1/M2/M4. It is not a model-logit gate.

The fragment layout was checked against [NVIDIA PTX ISA 8.5, m16n8k8 fragments](https://docs.nvidia.com/cuda/archive/12.6.3/parallel-thread-execution/index.html#warp-level-matrix-fragment-mma-1688) before integration. The existing nibble packing already pairs adjacent K columns; no weight permutation is needed.

### Bank-swizzle diagnosis

The initial direct load addresses are `(4*i+j)*cpr + group*4 + chunk` within each token column. `cpr` and each column's storage stride are multiples of 32 words. Therefore the distinct K pairs and token columns map to the same shared-memory bank. They are different addresses, not a broadcast [derived address model, `gemm_mma.cuh`].

After remapping, a B word is at `((chunk*16+4*i+j) XOR (column*4))`. For a fixed MMA step, the participating lanes map to distinct banks [derived address model]. This is not a measured bank-conflict counter.

The same-process dynamic-width comparison directly tests the change [measured, `shapes-dynamic-width.json`]:

### Issue work and register pressure

[derived static SASS, `bench/lm22/sass.py` -> `sass-counts.json`] One unrolled 128-K fragment body emits 16 `HMMA.1688.F32`, 32 indexed shuffles, 32 half2 subtracts, 32 half2 dequant FMAs, 32 shifts, 48 LOP3s and 16 shared loads. The recorded body has 275 thread instructions, excluding group loads and outer loop control. These are emitted instructions, not retired counters or measured stall cycles. Fragment preparation still costs much more than the 16 MMA instructions alone imply.

[measured, `build_probe.sh` -> `builds.json`] Every timed standalone probe is spill-free. Final swizzled split-1 probe registers are 58/63/64 at M1/M2/M4. At M3/M5/M6/M7/M8 they are 64/64/68/77/84. M8 uses 49152 bytes of shared memory. Split-K scratch adds 8192 bytes at 512 threads in the tested split-4/8 M1/M2/M4 probes.

[measured, `build.sh mma` -> `builds.json`] Inlining the all-MMA path into the persistent kernel gives:

|---|---:|---:|---:|---:|
| 1 | 120 | 0 | 0 | 0 |
| 2 | 128 | 0 | 0 | 0 |
| 3 | 128 | 0 | 0 | 0 |

The M5 matvec-only entry also spills 60/60 bytes. No spilled build was timed.

[INFERENCE] The standalone fragment's modest register count does not survive whole-megakernel integration. At 512 threads the register allocation reaches 128 registers per thread. The in-place staging snapshot grows from up to nine words per thread at M3 to twelve at M4, while packed A operands, accumulators and the persistent phases compete in the compiler's allocation. The compile result proves register pressure; no variable-level liveness or hardware occupancy-counter attribution was performed.

## Honest negatives

- The target, GEMM M4-minus-M1 increment <=0.35 ms, was not achieved or measured for a valid replacement engine. The integrator selected no GEMM change.
- Full-pass M1/M2/M4 timing, persistent detailed-phase timing and full-model gate tiers were stopped by the integrator after the shape evidence. The copied engine and detail profiler remain available, but there is no claim they were run.
- No mixed CUDA/MMA dispatch is presented as sequential-exact. Real-row MMA and CUDA outputs differ even when both approximate the same CPU reference.
- No all-MMA model-logit gate was run. The all-MMA M4/M5 builds spill and are only compiler diagnostics.
- The kernel can exploit more token columns with little additional MMA arithmetic, but the measured M4 wins do not establish useful batch-1-to-M4 pass scaling.
- The schedule is unchanged. No new schedule-ACCEPT result is claimed or needed for the unchanged merge candidate.
- The first shape run stopped at a wrong head key after four shapes. The completed, corrected final five-shape run is the selection evidence.

## Open threads

[INFERENCE] For this retained INT4 layout, Turing m16n8k8 needs cheaper fragment preparation and a way to amortize it before it can beat CUDA cores at M1/M2. A dedicated GEMM kernel could retain B fragments across output tiles, distribute K across warps only for small row counts, and keep staging lifetimes separate from attention/prologue register allocation. A compact GEMM-local staging tile could also avoid whole-activation register snapshots. Those are design hypotheses, not implemented performance results. Repacking the weight files is outside this assignment and was not used.

The useful result from this attempt is narrower: fix the B bank mapping first. Without that, direct-register MMA is two to three times slower at M4 even though the weights are shared. With it, the skinny-shape advantage remains small and does not justify a new arithmetic contract this wave.
