## Status

Owned implementation is in `kernels/megakernel_mt/`; the engine bridge, gates and timing tools are in `bench/lm14/`. Existing v2, scale, benchmark and validator packages were not edited. No git writes were performed.

Both modes use the same weight-sharing GEMM and persistent phase path. Causal columns share one cache, have consecutive positions, append every new K/V row before attention, and mask each query at its own position. Batch-K columns have separate caches and positions. Logits and sampled argmax tokens are column-major outputs. Input tokens are teacher-forced inputs to a pass, not an attempt to generate several dependent unknown tokens at once.

The selected retry keeps activation columns in scalar-transposed shared memory. For a given half2 offset, consecutive lanes address consecutive words and distinct banks. Each INT4 chunk is loaded once per output row and lane, unpacked once, converted to FP16 weights once, and reused across all columns. Only the current column's activation operand is live. FP32 row sums combine the inherited four HFMA2 partial chains. Full FP32 row accumulation is retained as a measured alternate candidate, not falsely claimed as the selected arithmetic.

The retry reaches the requested occupancy target for M=4: 36 CTAs, 1024 threads, 64 registers, 34176 shared-memory bytes and zero spill stores/loads `[measured, build.sh -> build-m4.log]`. M=1/2/3 also use 1024 threads and 64 registers, with shared-memory footprints 20096/22144/25984 bytes. M=5 needs 512 threads and 124 registers, with 42048 shared-memory bytes, to retain zero spills `[measured, build-m{1,2,3,5}.log]`. The attention partition remains the original 32 virtual warp ranges even when physical warp count changes `[derived, mega_mt.cu]`.

M>1 adds one append barrier per layer. The implemented schedule has 171 phase flags versus 143 at M=1 `[derived, sched_mt.py]`. Schedule emission uses the runtime cache stride `ctx+8`, not v2's fixed allocation stride. Twelve JSONs cover both modes, M in {1,2,4}, and contexts 128/2048. Every one returned ACCEPT `[measured, kernels/megakernel_mt/sched_mt.py -> bench/lm14/schedules.json]`. IR acceptance proves dependency/address consistency, not kernel equivalence.

### SASS and the integrator's throughput bound

For the hidden-width standalone GEMM row loop, static whole-loop instruction density rises from 8.25 to 22.09375 thread instructions per weight at M=1 versus M=4. The emitted bodies contain 16 versus 64 LDS instructions, and 32 versus 80 HFMA2 instructions, respectively `[derived, bench/lm14/sass.py -> sass.json, mt_matvec NC=1 row-loop ranges]`. Those counts include affine weight dequantization and both predicated output/reduction paths. They are static upper bounds, not measured retired instructions. CUDA 13.3 also outlines repeated WARPSYNC/SHFL reductions into helper calls. No per-SASS stall counters are available here.

The integrator supplied a throughput-only bound, reproduced by `bench/lm14/bound.py -> bound.json`. Rounded inputs of approximately 600 million weights and 1.8 GHz are `[assumed, bound.py]`; the arithmetic below is `[derived, bound.py]`.

- Per SM, approximately 600M / 36 = 16.7M weights, or 8.35M half2 pairs.
- M=4 SMEM reads need approximately 1.04M cycles, or 0.58 ms, versus approximately 0.15 ms at M=1. This assumes one LDS.32 per lane per pair per column and 64 weights per warp-cycle per column.
- M=4 HFMA2 work is approximately 33.4M operations per SM / 64 lanes per clock = 0.52M cycles, or 0.29 ms.
- The resulting throughput estimate is near max of the measured 1.36 ms weight stream and roughly 0.6-0.9 ms compute. Allowing overhead gives approximately 1.4-1.6 ms and a roughly 1.1-1.2x GEMM ratio, rather than the measured 4.10 ms and 3.0x.

That leaves approximately 2.5 ms unexplained by the throughput estimate `[derived, bound.py]`. The leading hypothesis is latency from dependent LDS-to-HFMA2 chains and limited independent accumulators per warp, not raw SMEM/FMA throughput `[INFERENCE, integrator assessment; not a measured stall diagnosis]`. The bound intentionally omits dependency latency, control flow, reduction-helper overhead and other resource interactions.

## Honest negatives

- The retry restored full M=4 occupancy and zero spills but did not meet the kill line. It does not show that Turing cannot process a skinny GEMM efficiently.
- The current attention loop scans the cache once per column, even in causal mode. No shared-KV-read performance claim is made.
- The pure FP32 and optimized MMA alternate candidates were timing/bring-up probes, not fully gated replacement engines. MMA output is finite and its one-position difference from the selected candidate is 0.03313947 `[measured, choose.py]`; that is not a substitute for the full gate.
- Final correctness uses short generated-prompt contexts, exactly the teacher-forced gate protocol. No final context-2048 or context-8192 runtime gate/timing claim is made.
- Contexts 2048/8192 timing and the 1.7B port are absent because the binding kill line stopped the experiment. Static context-2048 schedules still ACCEPT.
- Initial fixed-capacity cache allocation failed with CUDA OOM when the smoke retained a reference-cache clone alongside batched caches. Runtime-sized cache strides fixed that allocation problem before the full gate. The temporary smoke was deleted after the permanent gate covered both modes.
- Clocks are unlocked. Cross-session absolute latency changes are not speedup claims. All reported speed ratios come from same-process alternation.

## Open threads

The first next step is per-SASS stall analysis, or a focused benchmark of one real GEMM shape at M=1 versus M=4. The question is where the approximately 2.5 ms gap above the throughput estimate goes. Separate dependent SMEM operand latency, reduction-helper overhead and row/output control flow before trying another model or more fusion.

The bounded retry is complete. This package is not a v2 replacement, and no performance claim extends beyond the measured short-context pass curves.
